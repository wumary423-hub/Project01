# 船只资产制作全局规则

本规则适用于 Project01 中**所有船只资产**的设计与视觉制作，包括文字讨论、概念设计、概念图、直接改图、材质卡应用、后续多视图与最终生产输入。

单船 `design.md`、`integration.yaml` 和专属材质卡可以增加更具体的限制，但除非用户明确修改本规则，否则不得用单次生成习惯、聊天历史或模型默认行为削弱本规则。

## 1. 默认工作方式：先分析文字，再考虑作图

1. 收到船只资产任务后，第一动作是读取当前有效规则并分析用户文字，不得因为最终工作流目标是出图就直接触发图像生成。
2. **讨论、评审、问题诊断、规则修改、材质分析、方案比较、流程调整**默认只做文字工作；除非用户明确要求生成图片，否则不得自行出图。
3. 用户明确使用“出图 / 生成 / 绘制 / 重出 / 重新出”等表达时，才进入图像输出流程；即使如此，也必须先完成规则与上下文核对，再生成。
4. “提到了图片”不等于“要求生成图片”。多数制作交流应保持为文字交流。

## 2. 游戏开发内容：规则读取第一优先

1. 任何船只资产制作任务，都必须先读取 Git 当前分支中的权威规则，不得先从聊天历史或模型记忆构造需求。
2. 船只视觉/制作允许使用的受控来源包括：
   - `spec-manifest.yaml`；
   - `Docs/governance/source-of-truth.md`；
   - 船只系统规范；
   - 本文件；
   - 目标船只当前 `design.md` / `integration.yaml`；
   - 当前任务明确指定的材质卡；
   - 用户当前消息中的明确要求。
3. **历史聊天、已删除会话、模型记忆、旧提示词、助手以前自己写的描述、自动 caption、被否决图片、未批准生成图**均不得作为设计事实源。
4. 规则或材质卡无法实际读取时，必须明确说明；不得用“典型帆船”“历史常识”“以前好像是这样”等内容偷偷补齐。
5. 用户当前明确指令可以提出或批准规则变更；涉及 `LOCKED` 内容时，仍按治理规则写入规范、ADR/Changelog 并提交 Git 后成为跨会话事实。

## 3. 操作模式必须先判定

### 3.1 直接改图（Edit Existing Image）

当用户明确要求“在这张图上改”“修改这张图”或直接对当前图片提出修改时：

- 以该图片本身作为直接编辑基准；
- 不得把任务擅自转换成从头重画；
- 只处理用户明确要求修改的内容，未要求整体重设计时，不主动改动其他区域或设计关系；
- 当前权威的结构、材质和颜色硬约束仍然有效，除非用户在本次指令中明确修改这些规则。

### 3.2 重新 / 重出（Clean-Slate Regeneration）

用户使用“重新”“重出”“从头做”“推翻上一版”等表达时，默认表示**推翻上一版生成结果并从规则重新生成**。

此模式只允许读取：

- 当前有效的权威文字规则；
- 当前目标资产的文字设计档案；
- 当前有效材质卡；
- 用户本次消息中的明确要求。

此模式禁止读取或使用为生成输入：

- 上一版概念图或上一版生成图；
- 之前的 Concept Master / 视觉母图图片本身；
- 被否决图片；
- 历史提示词和历史出图 brief；
- 历史聊天中的临时视觉描述；
- 模型记忆或助手以前自行总结的风格词。

**“重新出概念图”不是“基于旧概念图优化”。** 旧视觉母版仍可作为版本档案保留，但不得作为本次 clean-slate 生成的图片参考输入。已经正式转写进当前文字规范的结构事实仍然有效。

只有用户明确说“基于母图修改”“参考上一版”“在这张图上改”等，才允许把指定旧图作为视觉参考/编辑基准。

## 4. [概念图] 的职责

1. `[概念图]` 默认是一张用于**定调**的关键概念图，不默认制作多视图。
2. 它负责确定整体设计调子，例如：主体轮廓、体量与比例关系、结构视觉重点、材质与颜色关系、整体表现语言。
3. 除非用户明确要求，不得把 `[概念图]` 自行扩展成：侧/前/后/顶等多视图板、材质球板、零件拆解板、细节特写集合或 UI 式 concept sheet。
4. 多视图属于后续明确命名的多视图阶段或用户单独要求，不应混入“概念图定调”任务。
5. 概念图在用户批准前只是候选稿；未批准图不得进入活跃权威路径。

## 5. 材质卡是硬约束，不是灵感参考

1. `MAT-*` 材质卡属于生成与制作的**硬约束**。不得把材质卡理解成“参考方向”“大概风格”或“可以自由发挥的灵感板”。
2. 任务指定某个材质卡时，生成前必须实际读取该卡当前权威版本；读不到就不得假装知道，也不得用模型默认材质替代。
3. **颜色严格服从材质卡。** 船只资产本体的木材、帆布、索具、金属、涂装、装饰等不得自行加入材质卡未定义的颜色。需要新增颜色时，必须先由用户修改/批准材质卡。
4. 光照与环境不得造成明显色偏，使材质卡外颜色被读成船只本体的新材质色。
5. 表面状态同样严格服从材质卡。材质卡未明确允许的污渍、褪色、磨损、锈蚀、泛黄、盐痕、附着物等效果不得自行添加。
6. 当前 `MAT-001` 的具体颜色与表面状态以其自身权威文件为唯一来源；本规则不复制其色值，避免形成第二套事实。
7. 材质卡只控制其声明范围内的材质、颜色、粗糙度和表面表现，不得借材质卡修改船型结构、桅杆数量、炮窗数量、甲板层级、船楼、舵、货舱口等结构设计。
8. 材质卡的参考图是否可以参与生成，必须服从材质卡自身的 `reference usage`。如果标记为仅存档，则不得把参考图喂给生成模型。

## 6. 禁止模型自行补设计

1. 不得因为“更真实”“更好看”“更有海洋感”“更有历史感”而自行增加规则没有的颜色、装饰、磨损、武器、货物、结构或视觉主题。
2. 不得从以前生成过的提示词中复活已经删除或替换的规则。
3. 规则中明确删除的设计倾向立即失效；旧聊天里即使仍有相关词语，也不得重新参与设计决策。
4. 对未锁定项目，不得把猜测写成正式设计事实。需要视觉候选时，只能保持最小、可逆、不会覆盖硬约束的处理。

## 7. 视觉母版的使用边界

视觉母版不是所有图像任务的无条件输入：

- **直接改图 / 明确要求参考母版：** 可以读取指定母版并在其基础上操作；
- **重新 / 重出：** 不读取旧母版图片，只读取当前权威文字规则；
- **普通文字讨论：** 没有必要时不加载图片，更不得因为存在母版就自动出图。

因此，“视觉母版是正式版本记录”与“重新出图时不参考旧母版”并不冲突：前者控制版本档案，后者控制本次生成输入。

## 8. 工具执行与持久化

1. 所有参与船只资产制作的工具都应在读取单船 `design.md` 前读取本规则。
2. 工具适配指南只能解释如何执行本规则，不得复制并长期维护另一套相互冲突的制作事实。
3. 本规则写入 Git 后即为跨会话、跨工具的船只资产制作规则；聊天存在与否不影响其效力。
4. 若任何旧工具指南与本规则冲突，以当前 Git 中状态/版本更高且权威层级更高的规范与本规则为准，并应修正旧指南。
