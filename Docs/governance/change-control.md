# 规范变更控制

## 1. 基本闭环

所有正式变更按以下步骤完成：

1. 读取当前 commit 对应的权威规范；
2. 明确变更对象、原因和影响；
3. 生成候选差异；
4. 用户审核；
5. 更新 Markdown、YAML、ADR 和 Changelog；
6. 运行校验；
7. 提交 Git；
8. 其他工具读取新的 commit。

## 2. LOCKED 内容

修改 `LOCKED` 内容必须满足：

- 用户明确批准；
- 说明哪些旧结论被改变；
- 创建或更新 ADR；
- 提高相关版本；
- 保留被替代文件或记录；
- 不得依赖聊天中的模糊同意推定批准。

## 3. 变更分类

### 3.1 澄清

不改变行为或视觉要求，可增加 Patch 版本。

### 3.2 非破坏性扩展

增加新字段、新模块或新阶段，可增加 Minor 版本。

### 3.3 破坏性变更

改变接口、模块名、Socket、尺寸基准、锁定轮廓或程序合同，需要 Major 版本或新的资产修订。

## 4. 决策记录

以下情况应创建 ADR：

- 选择或改变主工作流；
- 锁定视觉母版；
- 改变模块化边界；
- 改变程序接口；
- 放弃一种工具或生成方式；
- 修改 LOCKED 结论。

## 5. 候选输出

工具可以直接创建候选文件，但应满足：

- 新文件状态为 `DRAFT` 或 `REVIEW`；
- 不覆盖 LOCKED 原件；
- 同时提供差异摘要；
- 明确哪些字段仍为 `UNSET`；
- 不把猜测写成确定事实。

## 6. Single Developer Mode

本项目为单人独立开发。Git 仓库默认：

| 项 | 默认 |
|----|------|
| 读权限 | public |
| 写权限 | public |
| 创建文件 | Allowed |
| 修改文件 | Allowed |
| 新增资产档案 | Allowed |

不需要：

- Pull Request 流程；
- 分支审批；
- 额外的人工权限确认 / 多人 ACL。

仍必须：

- **不删除**已有规范；
- **不覆盖** `LOCKED` 设计内容（改 LOCKED 仍需用户明确批准 + ADR + 版本）；
- **不修改**已发布资产版本（已引用且 LOCKED 的视觉母版 / 已发布合同），除非用户明确要求；
- 不把猜测写成程序接口或精确尺寸。

关键锁定仍应保留清晰 diff、校验、明确 commit，以及用户对 LOCKED 变更的批准记录。
